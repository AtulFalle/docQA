# Observability standards

Stack: structlog JSON logs, OpenTelemetry traces and metrics to Grafana LGTM, Langfuse for LLM traces. Logs carry `trace_id`/`span_id` automatically.

## Logs

- Use `get_logger(__name__)`; event names are `component.noun.verb` in lower case: `ingest.chunk.completed`, `search.acl_filter.applied`. **[Enforced: ruff TID251/G; naming Review]**
- Fields are key-value, snake_case, stable names. Standard fields: `request_id`, `trace_id`, `tenant_id`, `doc_id`, `document_version_id`, `job_id`, `workflow_id`, `duration_ms`, `count`, `error`.
- Levels: `debug` dev detail; `info` state changes and milestones; `warning` recoverable/degraded; `error` operation failed (with `exc_info`); never log an error and re-raise at every layer, log once where handled.
- **Never log**: secrets, tokens, passwords, connection strings, PII (emails, names beyond ids), raw questions or answers, document text, chunk text, prompts, embeddings. **Log IDs, not text.** Counts, sizes and hashes are fine. **[Review]**
- Bind request or job context once with `docqa_core.logging.log_context(...)` / `bind_log_context(...)` (Python) or `setRequestUser(...)` from `apps/backend/src/common/request-context.ts` (NestJS), not on every call.

```python
# bad
log.info("answering", question=question, chunks=chunk_texts)
# good
log.info("query.answer.started", tenant_id=str(tenant_id), question_len=len(question), top_k=k)
```

## Traces

- Trace every external call: DB, Qdrant, Redis, object storage, LLM, embedder, Temporal, outbound HTTP. Wrap with a span if auto-instrumentation does not cover it. **[Review]**
- Span names `component.operation`, low cardinality: `qdrant.search`, `llm.generate`, `embed.batch`, `ingest.extract`. No ids or text in the name.
- Attributes: `tenant_id`, `doc_id`, `index_version`, `model`, `model_version`, `chunk_count`, `top_k`, token counts, `cache_hit`. **Never content** (text, prompts, completions). **[Review]**
- Record exceptions on spans and set error status; do not swallow them.
- Prompts and completions go to Langfuse only, per its retention/PII configuration, and never for tenants that opt out. Decide with the data-residency ADR.

## Metrics

- Names `docqa_<component>_<thing>_<unit>`: `docqa_ingest_documents_total`, `docqa_search_latency_seconds`, `docqa_llm_tokens_total`. Counters end `_total`, durations in seconds, sizes in bytes.
- Labels are low cardinality (`status`, `model`, `stage`, `outcome`). **Never** `doc_id`, `user_id`, `request_id`, or raw `tenant_id` on high-volume metrics; use traces/logs for per-id detail.
- Cover the RED signals (rate, errors, duration) for every endpoint and workflow stage, plus queue depth, ingest lag, retrieval latency, cache hit rate.

## Cost attribution

- Every LLM and embedding call records `tenant_id`, `model`, `model_version`, `input_tokens`, `output_tokens`, `purpose` (`embed`, `rewrite`, `answer`, `judge`) on its span and in the usage record. **[Review]**
- Aggregate cost per tenant from those records (SQL or metrics with a bounded tenant label for known tenants only); alert on anomalies.
- Track vector storage and object storage per tenant.

## Correlation

- `X-Request-ID` is accepted or generated by middleware, returned on every response, bound into logs, set on the root span and stored on audit rows.
- Propagate W3C `traceparent` to outbound HTTP and into Temporal (start workflows with trace context) so ingestion jobs link back to the API call.
- Errors shown to clients include `request_id`; support can find the trace from it. The web app shows it as "Reference" on error states.

### Shared log fields

Every service writes one JSON object per line to stdout and sends the same record over OTLP to Loki.

| Field | Backend (pino) | Python (structlog) | Notes |
|---|---|---|---|
| `service`, `env` | yes | yes | `docqa-backend`, `docqa-ai-api`, `docqa-worker`; env is `local`/`dev`/`staging`/`prod` |
| `request_id` | yes | yes | Same value in every service for one request; forwarded backend -> ai-api |
| `trace_id`, `span_id` | yes | yes | W3C IDs of the active span |
| `tenant_id`, `user_id` | when known | when bound | Set by auth (M1c) |
| `workflow_id`, `workflow_run_id`, `activity`, `attempt` | - | worker | Bound by `LogContextInterceptor` |
| `level`, `timestamp` | yes | yes | Level label and ISO-8601 UTC |
| message | `msg` | `event` | |

### Finding everything for one request

Given a `request_id` (from an error reference, a response header or a log line):

1. Grafana (http://localhost:3002 locally) -> Explore -> Loki:
   `{service_name=~"docqa-.*"} | request_id="<id>"` shows every log line from every service.
2. Copy `trace_id` from any line, then Explore -> Tempo -> paste the trace id to see the spans across backend, ai-api and the worker.
3. From a trace, "Logs for this span" goes back to Loki.

`make verify-observability` (with `make up-app` running) and the `observability` CI job check this end to end: one request must produce Loki logs from backend and ai-api with the same `request_id` and `trace_id`, and a Tempo trace with spans from both.

## Alerts and SLOs

- Define SLOs per user-facing path (e.g. p95 answer latency, availability, ingest freshness). Alerts fire on symptoms (SLO burn, backlog growth), not on every error.
- New feature = new dashboards/alerts decision in the PR: "none needed" is a valid, stated answer.
